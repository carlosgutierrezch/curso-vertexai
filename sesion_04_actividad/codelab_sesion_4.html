1. Introducción y arquitectura

Bienvenido al codelab de la Sesión 4 del curso. En las próximas dos horas vas a construir, paso a paso, un pipeline real de Career Path Analytics sobre los datos anonimizados de Personio que ya tenemos cargados desde la Sesión 1.

Este modulo es una fusión práctica de los Módulos 7 (SQL avanzado) y 8 (Dataform). Cada concepto SQL aparece dentro de un SQLX de Dataform que se ejecuta de verdad y produce una tabla que el equipo de RRHH puede usar mañana.

Las 3 preguntas de negocio que vas a contestar

El equipo de RRHH del cliente quiere responder a tres preguntas que hoy nadie en la organización sabe contestar de forma consistente:

  1. ¿Qué porcentaje de empleados ha sido promocionado en los últimos 12 meses? Y dentro de eso, ¿en qué países y bandas se concentra?
  2. ¿Qué cohorte de contratación tiene mayor riesgo de salida? ¿La gente que entra en Q1 se queda más que la que entra en Q3?
  3. ¿Cómo evolucionan los salarios cuando alguien pasa de banda P2 a P3? ¿Hay un patrón de subida o se mantiene el rango anterior?

Las tres preguntas requieren window functions, métricas temporales, CTEs estructurados, SCD2 y tests de calidad.Es decir: todos los temas del M7 y del M8.

3. Window functions sobre salary_history

En esta sección vas a comparar el salario de cada empleado contra el de su mes anterior usando LAG y a detectar variaciones salariales sin caer en el anti-patrón del self-join. Los conceptos que aprendas aquí los reutilizarás en el cap. 5 para detectar promociones sobre el SCD2.

Por qué window functions

Una pregunta del cliente: "¿en qué meses cada empleado tuvo una subida salarial superior al 5%?". Con GROUP BY es imposible: el agrupamiento colapsa filas y se pierde la dimensión temporal. Las window functions, en cambio, calculan una columna nueva preservando todas las filas originales. Por eso son la herramienta correcta para análisis longitudinal de personas: comparar a alguien con su propio pasado, no con sus compañeros.

Regla mental GROUP BY agrega entre filas y las colapsa. OVER (PARTITION BY ... ORDER BY ...) calcula entre filas pero las mantiene. Si necesitas ver el detalle y un agregado a la vez, casi siempre es window function.

Paso 1: explorar fact_salary_history

Antes de escribir window functions, echa un vistazo rápido a la tabla con la que vas a trabajar. silver_personio.fact_salary_history contiene snapshots mensuales de compensación de cada empleado durante 2025, construidos en el M2 a partir del CSV original de Personio. Empieza por una fila de muestra:

SQL · Inspeccionar fact_salary_history 
SELECT
  employee_code,
  snapshot_month,
  band,
  base_salary_eur,
  bonus_eur
FROM `silver_personio.fact_salary_history`
WHERE employee_code = (
  SELECT employee_code
  FROM `silver_personio.fact_salary_history`
  ORDER BY snapshot_month
  LIMIT 1
)
ORDER BY snapshot_month;

Deberías ver entre 6 y 12 filas, todas del mismo empleado, una por mes. La granularidad de la tabla es una fila por empleado y mes. Ese orden temporal dentro de cada empleado es lo que hace que las window functions tengan sentido aquí.

Paso 2: detectar variaciones salariales con LAG

El operador LAG(col) devuelve el valor de col en la fila anterior dentro de la partición. Combinado con PARTITION BY employee_code ORDER BY snapshot_month, te da el salario del mes previo para cada empleado:

SQL · Detectar subidas salariales > 5% 
WITH variaciones AS (
  SELECT
    employee_code,
    snapshot_month,
    base_salary_eur,
    LAG(base_salary_eur) OVER (
      PARTITION BY employee_code
      ORDER BY snapshot_month
    ) AS salario_mes_anterior
  FROM `silver_personio.fact_salary_history`
)
SELECT
  employee_code,
  snapshot_month,
  salario_mes_anterior,
  base_salary_eur,
  ROUND(SAFE_DIVIDE(base_salary_eur - salario_mes_anterior, salario_mes_anterior) * 100, 2) AS variacion_pct
FROM variaciones
WHERE salario_mes_anterior IS NOT NULL
  AND base_salary_eur > salario_mes_anterior * 1.05
ORDER BY variacion_pct DESC
LIMIT 20;

El filtro salario_mes_anterior IS NOT NULL es importante: LAG devuelve NULL en la primera fila de cada empleado (no hay mes anterior). Sin ese filtro, contarías la primera observación de cada empleado como una "variación" inexistente.

Resultado esperado sobre el dataset Personio: entre 8 y 15 filas, principalmente empleados que tuvieron una revisión salarial en mitad de año.

Paso 3: el anti-patrón que no debes copiar

Antes de window functions, este problema se resolvía con un self-join sobre la misma tabla con offset de 1 mes. Funciona, pero lee la tabla dos veces y escala mal. Ejecuta esta versión y compara los bytes leídos con el paso 2:

SQL · Anti-patrón con self-join 
-- NO HACER ESTO EN PRODUCCIÓN
SELECT
  hoy.employee_code,
  hoy.snapshot_month,
  ayer.base_salary_eur AS salario_mes_anterior,
  hoy.base_salary_eur,
  ROUND(SAFE_DIVIDE(hoy.base_salary_eur - ayer.base_salary_eur, ayer.base_salary_eur) * 100, 2) AS variacion_pct
FROM `silver_personio.fact_salary_history` hoy
LEFT JOIN `silver_personio.fact_salary_history` ayer
  ON hoy.employee_code = ayer.employee_code
  AND ayer.snapshot_month = DATE_SUB(hoy.snapshot_month, INTERVAL 1 MONTH)
WHERE ayer.base_salary_eur IS NOT NULL
  AND hoy.base_salary_eur > ayer.base_salary_eur * 1.05
ORDER BY variacion_pct DESC
LIMIT 20;

El resultado es el mismo. El coste, no. Mira el panel Job Information > Bytes processed en BigQuery después de cada query:

PatrónBytes leídosVeces que escanea la tabla
LAG (window function)~120 KB1
Self-join con offset~240 KB2
Por qué importa en producción Sobre los 1.189 registros de Personio la diferencia es invisible (céntimos). Sobre la tabla equivalente de un cliente real con 100k empleados y 5 años de histórico, el self-join multiplica por 2 los bytes facturados de cada job. Si la query corre cada noche detrás de un dashboard, el sobrecoste anual es real.

Paso 4: ROW_NUMBER y FIRST_VALUE

Otras dos window functions que vas a usar muy pronto en el pipeline:

  • ROW_NUMBER(): numera las filas dentro de cada partición. Sirve para quedarte con la fila "primera" o "última" de cada grupo (por ejemplo, el snapshot más reciente de cada empleado).
  • FIRST_VALUE(col): devuelve el valor de col en la primera fila de la partición. Sirve para llevar el baseline al lado de cada fila (por ejemplo, el salario al hire).

Esta query combina ambas para mostrar, junto al salario actual de cada empleado, su salario inicial y su variación acumulada:

SQL · ROW_NUMBER + FIRST_VALUE + QUALIFY 
SELECT
  employee_code,
  snapshot_month,
  band,
  base_salary_eur,
  FIRST_VALUE(base_salary_eur) OVER (
    PARTITION BY employee_code
    ORDER BY snapshot_month
  ) AS salario_baseline,
  ROUND(
    SAFE_DIVIDE(
      base_salary_eur - FIRST_VALUE(base_salary_eur) OVER (
        PARTITION BY employee_code ORDER BY snapshot_month
      ),
      FIRST_VALUE(base_salary_eur) OVER (
        PARTITION BY employee_code ORDER BY snapshot_month
      )
    ) * 100, 2
  ) AS variacion_acumulada_pct,
  ROW_NUMBER() OVER (
    PARTITION BY employee_code
    ORDER BY snapshot_month DESC
  ) AS fila_desde_mas_reciente
FROM `silver_personio.fact_salary_history`
QUALIFY fila_desde_mas_reciente = 1
ORDER BY variacion_acumulada_pct DESC;

La cláusula QUALIFY es la forma BigQuery-native de filtrar por el resultado de una window function sin envolverla en un CTE intermedio. Aquí te quedas con una sola fila por empleado (la más reciente), comparada contra su salario inicial.

4. Construir dim_employee_scd2 con MERGE

En esta sección vas a construir tu primera tabla del pipeline: dim_employee_scd2. Es una tabla histórica que captura cada cambio en los atributos del empleado (banda, departamento, manager, país) como una fila nueva, con fechas de validez. Esto se llama Slowly Changing Dimension Tipo 2 (SCD2) y es el patrón estándar para responder a preguntas del tipo "¿cuál era la banda de Juan el 15 de marzo de 2024?".

Qué tabla vas a crear

Columna Tipo Significado
employee_codeSTRING NOT NULLIdentificador del empleado
countrySTRINGPaís en este intervalo de tiempo
bandSTRINGBanda salarial (P1-P3, E1-E2, M2-M3)
departmentSTRINGDepartamento
manager_codeSTRINGManager en este intervalo
effective_fromDATE NOT NULLFecha desde la que esta versión es válida
effective_toDATEFecha hasta la que esta versión fue válida (NULL si es la actual)
is_currentBOOL NOT NULLTRUE si esta es la versión vigente del empleado

Paso 1: crear el SQLX en Dataform

Crea un nuevo archivo en tu workspace Dataform en la ruta definitions/dim_employee_scd2.sqlx con el siguiente contenido. Este SQLX define la tabla particionada por effective_from y clusterizada por employee_code:

definitions/dim_employee_scd2.sqlx 
config {
  type: "incremental",
  schema: "career_analytics",
  description: "Dimensión SCD2 del empleado. Una fila por intervalo de tiempo en el que sus atributos (banda, depto, manager) fueron constantes.",
  bigquery: {
    partitionBy: "effective_from",
    clusterBy: ["employee_code", "is_current"]
  },
  assertions: {
    nonNull: ["employee_code", "effective_from", "is_current"],
    uniqueKey: ["employee_code", "effective_from"]
  }
}

-- Primera ejecución: poblar desde dim_employee con effective_from = hire_date
-- Ejecuciones siguientes: MERGE con cambios detectados en silver_personio.dim_employee

MERGE ${self()} t
USING (
  SELECT
    employee_code,
    country,
    band,
    department,
    manager_code,
    CURRENT_DATE() AS effective_from
  FROM `${dataform.projectConfig.defaultDatabase}.silver_personio.dim_employee`
) s
ON t.employee_code = s.employee_code
   AND t.is_current = TRUE

-- Si el empleado existe en SCD2 y algún atributo cambió: cerrar la versión vigente
WHEN MATCHED AND (
  COALESCE(t.country, '') != COALESCE(s.country, '')
  OR COALESCE(t.band, '') != COALESCE(s.band, '')
  OR COALESCE(t.department, '') != COALESCE(s.department, '')
  OR COALESCE(t.manager_code, '') != COALESCE(s.manager_code, '')
) THEN
  UPDATE SET
    effective_to = s.effective_from,
    is_current = FALSE

-- Empleado nuevo o cambio detectado: insertar versión nueva
WHEN NOT MATCHED THEN
  INSERT (employee_code, country, band, department, manager_code,
          effective_from, effective_to, is_current)
  VALUES (s.employee_code, s.country, s.band, s.department, s.manager_code,
          s.effective_from, NULL, TRUE);

Paso 2: ¿qué hace este MERGE?

El MERGE es la pieza central del SCD2. Vamos paso a paso:

  1. Source (s): la "foto actual" de cada empleado en silver_personio.dim_employee. Cada empleado aparece una sola vez.
  2. Target (t): la tabla histórica que estás construyendo. Un mismo empleado puede aparecer N veces si ha cambiado N-1 veces de banda/departamento/manager.
  3. JOIN ON: solo nos interesa la versión vigente del empleado en la tabla histórica (is_current = TRUE).
  4. WHEN MATCHED AND (cambió algo): si algún atributo difiere, cerramos la versión vigente con un effective_to y la marcamos is_current = FALSE.
  5. WHEN NOT MATCHED: cubre dos casos. Empleado nuevo (no existe en la tabla histórica). O empleado existente cuyo MATCHED se cerró en el paso anterior y ahora insertamos su versión nueva.
Trampa común con NULLs El operador != devuelve NULL cuando uno de los operandos es NULL. Si no envuelves los atributos en COALESCE(..., ''), los cambios entre "valor" y NULL se te escaparán silenciosamente. Es un bug clásico de SCD2 que solo descubres meses después cuando los analistas reportan números raros.

Paso 4: simular un cambio y reejecutar

Para probar que el MERGE funciona correctamente, vamos a simular un cambio de banda en un empleado y reejecutar el SQLX. Este UPDATE temporal sobre silver_personio.dim_employee simula lo que ocurriría tras una ronda de promociones:

SQL · Simular promoción 
-- Tomar un empleado P2 y promocionarlo a P3
UPDATE `silver_personio.dim_employee`
SET band = 'P3'
WHERE employee_code = (
  SELECT employee_code
  FROM `silver_personio.dim_employee`
  WHERE band = 'P2'
  LIMIT 1
);

Ahora reejecuta el SQLX dim_employee_scd2 en Dataform. Y vuelve a contar:

SQL · Ver el cambio histórico 
-- Buscar empleados con más de una versión histórica
SELECT
  employee_code,
  band,
  effective_from,
  effective_to,
  is_current
FROM `career_analytics.dim_employee_scd2`
WHERE employee_code IN (
  SELECT employee_code
  FROM `career_analytics.dim_employee_scd2`
  GROUP BY employee_code
  HAVING COUNT(*) > 1
)
ORDER BY employee_code, effective_from;

Deberías ver al empleado promocionado con dos filas: la versión P2 cerrada (effective_to con la fecha de hoy, is_current = FALSE) y la versión P3 abierta (effective_to = NULL, is_current = TRUE).

Lo que acabas de construir Una tabla histórica completa que permite reconstruir el estado del empleado en cualquier momento del pasado con una query simple: WHERE effective_from <= '2024-06-15' AND (effective_to IS NULL OR effective_to > '2024-06-15'). Esto es la base del análisis longitudinal que viene en las siguientes secciones.

Paso 5: Dataform garantiza la idempotencia

Una pregunta razonable: ¿qué pasa si ejecutas el SQLX dos veces seguidas sin que haya cambios reales? La respuesta: nada. El bloque WHEN MATCHED AND (algo cambió) garantiza que solo se inserta una versión nueva cuando hay cambio real. La idempotencia es responsabilidad del SQL, no del orquestador.

Conexión con M5 (orquestación) Cloud Workflows puede invocar este SQLX cada noche sin riesgo. Si silver_personio.dim_employee no cambió, la tabla histórica no crece. Si hubo cambios, los captura automáticamente. Esa es la separación clean: Workflows decide cuándo, Dataform decide cómo.

5. Promociones y métricas temporales

En esta sección vas a usar lo que aprendiste en el cap 3 (window functions) sobre la tabla histórica del cap 4 (SCD2) para construir fact_promotions: una tabla con una fila por cada cambio de banda. Después le añadirás dos métricas temporales clave para People Analytics: tenure (tiempo total en la empresa) y time-in-band (tiempo desde la última promoción).

Paso 1: detectar transiciones con LAG sobre el SCD2

El SCD2 ya tiene una fila por cada periodo en el que la banda del empleado fue constante. Si ordenas por effective_from dentro de cada empleado y comparas con la fila anterior usando LAG, cualquier diferencia de banda es una transición. Crea este SQLX en Dataform:

definitions/fact_promotions.sqlx 
config {
  type: "table",
  schema: "career_analytics",
  description: "Una fila por cada transición de banda en la carrera del empleado. Tipos: HIRE, PROMOCION, DEGRADACION, CAMBIO_LATERAL.",
  bigquery: {
    partitionBy: "DATE(transition_date)",
    clusterBy: ["employee_code", "transition_type"]
  },
  assertions: {
    nonNull: ["employee_code", "transition_date", "band_to", "transition_type"]
  }
}

WITH transiciones AS (
  SELECT
    employee_code,
    band AS band_to,
    LAG(band) OVER (PARTITION BY employee_code ORDER BY effective_from) AS band_from,
    department,
    LAG(department) OVER (PARTITION BY employee_code ORDER BY effective_from) AS department_from,
    effective_from AS transition_date
  FROM `${dataform.projectConfig.defaultDatabase}.career_analytics.dim_employee_scd2`
)
SELECT
  employee_code,
  transition_date,
  band_from,
  band_to,
  department_from,
  department AS department_to,
  CASE
    WHEN band_from IS NULL THEN 'HIRE'
    WHEN SAFE_CAST(SUBSTR(band_to, 2) AS INT64) > SAFE_CAST(SUBSTR(band_from, 2) AS INT64) THEN 'PROMOCION'
    WHEN SAFE_CAST(SUBSTR(band_to, 2) AS INT64) < SAFE_CAST(SUBSTR(band_from, 2) AS INT64) THEN 'DEGRADACION'
    WHEN band_from = band_to AND department_from != department THEN 'CAMBIO_LATERAL'
    ELSE 'SIN_CAMBIO'
  END AS transition_type
FROM transiciones
WHERE band_from IS NULL OR band_from != band_to OR department_from != department;

El truco está en LAG(band) OVER (PARTITION BY employee_code ORDER BY effective_from): te da la banda anterior dentro del histórico de cada empleado. La primera fila del empleado tiene band_from = NULL, que clasificamos como HIRE (es la entrada inicial al SCD2, no una transición real).

El SUBSTR(band, 2) extrae el número de la banda ("P3" → "3") para poder comparar P2 vs P3 numéricamente. Funciona para nuestro esquema P1-P3/E1-E2/M2-M3 porque todas las bandas son letra + número. Si tu cliente usa otro esquema (Senior I/II/III, por ejemplo) tendrás que adaptar la lógica.

Ejecuta el SQLX desde Dataform y valida en tu notebook:

FROM `career_analytics.fact_promotions`
GROUP BY transition_type
ORDER BY eventos DESC;

Paso 2: tenure desde la fecha de hire

El tenure es el tiempo total que un empleado lleva en la empresa, medido desde su hire_date. Sirve para segmentar análisis (gente con menos de 6 meses no se evalúa igual que veteranos) y para el cohort retention que viene en el cap 6. Calcúlalo con DATE_DIFF:

SQL · Tenure por empleado (top 10) 
SELECT
  employee_code,
  hire_date,
  DATE_DIFF(CURRENT_DATE(), hire_date, MONTH) AS tenure_meses,
  DATE_DIFF(CURRENT_DATE(), hire_date, YEAR)  AS tenure_anios
FROM `silver_personio.dim_employee`
WHERE status = 'active'
ORDER BY tenure_meses DESC
LIMIT 10;

Deberías ver el top 10 de empleados con mayor antigüedad. La diferencia entre MONTH y YEAR en DATE_DIFF no es una división: cada uno cuenta el número de unidades cruzadas por completo. Por eso un empleado con tenure de 18 meses sale como 1 año, no 1.5.

Paso 3: time-in-band desde la última promoción

El time-in-band mide cuánto lleva el empleado en su banda actual. Es la métrica clave para detectar gente "atascada": un P2 que lleva 4 años en P2 sin haber subido es candidato a marcharse o a una conversación de carrera. Se calcula desde el effective_from de la versión vigente en el SCD2:

SQL · Empleados con 3+ años en la misma banda 
SELECT
  employee_code,
  band,
  effective_from AS desde,
  DATE_DIFF(CURRENT_DATE(), effective_from, MONTH) AS meses_en_banda
FROM `career_analytics.dim_employee_scd2`
WHERE is_current = TRUE
  AND DATE_DIFF(CURRENT_DATE(), effective_from, MONTH) >= 36
ORDER BY meses_en_banda DESC;

El filtro >= 36 te enseña empleados con 3 años o más en la misma banda. Sobre el dataset Personio aparecerán bastantes (es lo normal: la mayoría no han cambiado de banda en los datos disponibles), pero la query es exactamente la misma que correrías sobre datos reales con histórico de 5+ años para detectar los casos anómalos.

Insight de People Analytics Combinar tenure con time-in-band da una métrica derivada útil: "% del tenure pasado en la banda actual". Si un empleado lleva 8 años en la empresa y los últimos 6 en la misma banda, el 75% de su tenure ha sido sin progresión. Ese ratio es mucho mejor predictor de fuga que cualquiera de los dos por separado.

6. fact_career_events: CTEs y cohort retention

Hasta aquí tienes datos cargados (silver_personio), un histórico de bandas (dim_employee_scd2) y transiciones detectadas (fact_promotions). En esta sección vas a unir todo en una tabla unificada de eventos de carrera (fact_career_events) usando CTEs estructurados, y encima de eso vas a montar el análisis de cohort retention que pidió el cliente.

Por qué CTEs en vez de subqueries anidadas

Una query de 200 líneas sin CTEs es ilegible. Una query de 200 líneas con 6-7 CTEs nombrados se lee como un guión: cada CTE responde a una pregunta concreta y la siguiente la usa. Cuando un compañero abre tu SQL meses después, los nombres de los CTE le explican la lógica antes que el código.

Paso 1: construir fact_career_events con CTEs

Vas a unir tres tipos de evento (hires, transiciones de banda, bajas) en una tabla con un schema común. Crea este SQLX:

definitions/fact_career_events.sqlx 
config {
  type: "table",
  schema: "career_analytics",
  description: "Tabla unificada de eventos de carrera del empleado: HIRE, PROMOCION, DEGRADACION, CAMBIO_LATERAL, BAJA.",
  bigquery: {
    partitionBy: "DATE(event_date)",
    clusterBy: ["employee_code", "event_type"]
  }
}

-- 1) Empleados activos: base sobre la que vamos a buscar eventos
WITH empleados_activos AS (
  SELECT employee_code, hire_date, country, band AS band_actual
  FROM `${dataform.projectConfig.defaultDatabase}.silver_personio.dim_employee`
),

-- 2) Eventos de contratación: el primer registro de cada empleado
eventos_hire AS (
  SELECT
    e.employee_code,
    e.hire_date AS event_date,
    'HIRE' AS event_type,
    CAST(NULL AS STRING) AS band_from,
    e.band_actual AS band_to,
    e.country
  FROM empleados_activos e
),

-- 3) Eventos de transición: vienen de fact_promotions
eventos_transicion AS (
  SELECT
    p.employee_code,
    p.transition_date AS event_date,
    p.transition_type AS event_type,
    p.band_from,
    p.band_to,
    e.country
  FROM `${dataform.projectConfig.defaultDatabase}.career_analytics.fact_promotions` p
  JOIN empleados_activos e USING (employee_code)
  WHERE p.transition_type IN ('PROMOCION', 'DEGRADACION', 'CAMBIO_LATERAL')
),

-- 4) Eventos de baja: empleados con status != active
eventos_baja AS (
  SELECT
    employee_code,
    COALESCE(termination_date, CURRENT_DATE()) AS event_date,
    'BAJA' AS event_type,
    band AS band_from,
    CAST(NULL AS STRING) AS band_to,
    country
  FROM `${dataform.projectConfig.defaultDatabase}.silver_personio.dim_employee`
  WHERE status != 'active'
),

-- 5) Consolidar todos los eventos con el mismo schema
eventos_consolidados AS (
  SELECT * FROM eventos_hire
  UNION ALL
  SELECT * FROM eventos_transicion
  UNION ALL
  SELECT * FROM eventos_baja
)

-- 6) Output final con secuencia cronológica por empleado
SELECT
  employee_code,
  event_date,
  event_type,
  band_from,
  band_to,
  country,
  ROW_NUMBER() OVER (PARTITION BY employee_code ORDER BY event_date) AS event_seq
FROM eventos_consolidados
ORDER BY employee_code, event_date;

Cada CTE tiene una responsabilidad clara y un nombre que la describe. Si mañana tienes que añadir un nuevo tipo de evento (por ejemplo, cambios de país por relocation), añades un CTE eventos_relocation y lo metes al UNION. No tocas el resto.

Ejecútalo en Dataform y valida en tu notebook:

SQL · Validar fact_career_events 
SELECT event_type, COUNT(*) AS eventos
FROM `career_analytics.fact_career_events`
GROUP BY event_type
ORDER BY eventos DESC;

Paso 2: cohort retention por trimestre de hire

Ahora la pregunta de negocio: "¿qué cohorte de hires se queda más tiempo?". Una cohorte es un grupo de empleados con algo en común; en este caso, el trimestre en el que entraron a la empresa. Para cada cohorte calcularás qué porcentaje sigue activo a los 3, 6, 9 y 12 meses desde su hire.

La lógica:

  1. Asignar a cada empleado su cohorte de hire con DATE_TRUNC(hire_date, QUARTER).
  2. Calcular cuántos meses lleva activo cada uno: si tiene BAJA hasta esa fecha, si no hasta hoy.
  3. Para cada cohorte, contar cuántos empleados llegaron a 3/6/9/12 meses sin causar baja.
SQL · Cohort retention por trimestre de hire 
WITH base AS (
  SELECT
    employee_code,
    DATE_TRUNC(MIN(CASE WHEN event_type = 'HIRE' THEN event_date END), QUARTER) AS cohorte,
    MIN(CASE WHEN event_type = 'HIRE' THEN event_date END) AS fecha_hire,
    MIN(CASE WHEN event_type = 'BAJA' THEN event_date END) AS fecha_baja
  FROM `career_analytics.fact_career_events`
  GROUP BY employee_code
),
con_supervivencia AS (
  SELECT
    cohorte,
    employee_code,
    DATE_DIFF(COALESCE(fecha_baja, CURRENT_DATE()), fecha_hire, MONTH) AS meses_activo
  FROM base
  WHERE fecha_hire IS NOT NULL
)
SELECT
  cohorte,
  COUNT(*) AS tamano_cohorte,
  ROUND(100 * COUNTIF(meses_activo >= 3)  / COUNT(*), 1) AS retencion_3m_pct,
  ROUND(100 * COUNTIF(meses_activo >= 6)  / COUNT(*), 1) AS retencion_6m_pct,
  ROUND(100 * COUNTIF(meses_activo >= 9)  / COUNT(*), 1) AS retencion_9m_pct,
  ROUND(100 * COUNTIF(meses_activo >= 12) / COUNT(*), 1) AS retencion_12m_pct
FROM con_supervivencia
GROUP BY cohorte
HAVING COUNT(*) >= 5
ORDER BY cohorte;

El HAVING COUNT(*) >= 5 al final no es decoración: es k-anonimidad. Cohortes con menos de 5 empleados no se exponen porque sería trivial reidentificar a la persona concreta cuyos datos estás mirando. Es una protección obligatoria cuando el output va a un dashboard que verá gente fuera del equipo de RRHH.

Cuidado al interpretar las cohortes recientes Las cohortes más recientes tendrán retencion_12m_pct bajo de forma engañosa porque aún no ha pasado un año desde su hire. No es un bug: es que la métrica todavía no es calculable. En un dashboard real conviene marcar esas cohortes explícitamente como "datos incompletos" para no inducir a comparaciones sesgadas.

  2. Has ejecutado el cohort retention y entiendes por qué algunas cohortes salen con porcentajes bajos en los meses largos.

7. Capa semántica, tests y cierre

Última sección. Vas a empaquetar todo lo construido en una capa de consumo lista para Looker Studio (v_career_path_dashboard), añadirás tests automáticos en Dataform que detectan problemas de calidad antes de que lleguen al dashboard, y cerraremos con una nota sobre cómo conecta con el M14.

Paso 1: UDF reutilizable tenure_bucket

El concepto de capa semántica es: cada métrica de negocio se define una sola vez en un sitio y el resto del pipeline (vistas, dashboards, queries ad-hoc) la consume desde ahí. Sin capa semántica, cada analista escribe su propia versión de "tenure_bucket" y los números nunca cuadran entre dashboards.

Empieza por una UDF persistente que clasifica empleados por antigüedad. Crea este SQLX:

definitions/udf_tenure_bucket.sqlx 
config {
  type: "operations",
  hasOutput: false,
  description: "UDF persistente: clasifica tenure en meses en buckets estándar usados en todo el pipeline."
}

CREATE OR REPLACE FUNCTION `${dataform.projectConfig.defaultDatabase}.career_analytics.tenure_bucket`(meses INT64)
RETURNS STRING
AS (
  CASE
    WHEN meses < 6   THEN '0-6m'
    WHEN meses < 12  THEN '6-12m'
    WHEN meses < 24  THEN '1-2y'
    WHEN meses < 60  THEN '2-5y'
    ELSE '5y+'
  END
);

El bloque type: "operations" de Dataform sirve para statements DDL puros (CREATE FUNCTION, CREATE PROCEDURE) que no producen una tabla. hasOutput: false le dice a Dataform que no la trate como nodo del DAG con dependientes.

Paso 2: vista v_career_path_dashboard

Ahora la vista que consumirá Looker Studio. Solo expone agregados, nunca PII individual:

definitions/v_career_path_dashboard.sqlx 
config {
  type: "view",
  schema: "career_analytics",
  description: "Capa semántica para Looker Studio. Agregados por país, banda y tenure_bucket. K-anonimidad >= 5."
}

SELECT
  e.country,
  e.band,
  `${dataform.projectConfig.defaultDatabase}.career_analytics.tenure_bucket`(
    DATE_DIFF(CURRENT_DATE(), e.hire_date, MONTH)
  ) AS tenure_bucket,
  COUNT(*) AS headcount,
  COUNTIF(p.transition_type = 'PROMOCION') AS promociones_ultimo_anio
FROM `${dataform.projectConfig.defaultDatabase}.silver_personio.dim_employee` e
LEFT JOIN `${dataform.projectConfig.defaultDatabase}.career_analytics.fact_promotions` p
  ON e.employee_code = p.employee_code
  AND p.transition_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 12 MONTH)
WHERE e.status = 'active'
GROUP BY e.country, e.band, tenure_bucket
HAVING COUNT(*) >= 5;

Tres cosas importantes en esta vista:

  • Llama a la UDF tenure_bucket en vez de duplicar el CASE. Si mañana cambias los umbrales de los buckets, los cambias en la UDF y todos los dashboards se actualizan a la vez.
  • El HAVING COUNT(*) >= 5 es la misma protección de k-anonimidad del cap 6, aplicada también aquí para que la vista nunca exponga celdas con menos de 5 empleados.
  • Es una view (no table): cada vez que Looker Studio la consulta, BigQuery recalcula. Si el dashboard recibe muchos hits, conviene cambiarla a type: "table" con refresh diario via Cloud Workflows (lo vimos en M5).

Paso 3: tests automáticos con assertions

Hasta ahora has confiado en que las queries son correctas porque las has revisado tú. En producción no funciona así: los datos cambian todos los días y un cambio en el origen puede romper silenciosamente alguna premisa de tu pipeline. Las assertions de Dataform son tests SQL que se ejecutan después de cada SQLX y fallan ruidosamente cuando algo no encaja.

Ya has visto assertions inline en los config de los SQLX anteriores (nonNull, uniqueKey). Ahora añade una assertion custom con SQL libre, que es la pieza más potente. Crea este archivo:

definitions/assert_band_after_hire.sqlx 
config {
  type: "assertion",
  description: "Ningún empleado puede tener una banda asignada con effective_from anterior a su hire_date."
}

SELECT
  s.employee_code,
  s.effective_from,
  e.hire_date
FROM `${dataform.projectConfig.defaultDatabase}.career_analytics.dim_employee_scd2` s
JOIN `${dataform.projectConfig.defaultDatabase}.silver_personio.dim_employee` e
  USING (employee_code)
WHERE s.effective_from < e.hire_date;

La regla: una assertion falla si la query devuelve filas. Si el SELECT no devuelve nada, todo bien. Si devuelve aunque sea una fila, Dataform marca el run como fallido y bloquea los SQLX dependientes hasta que se arregle. Esto es tu seguridad de que el pipeline no propaga datos rotos al dashboard.

Qué hacer cuando una assertion falla en producción Lo primero, no la borres ni la silencies. La assertion está diciéndote que una premisa que dabas por cierta ya no lo es. Investiga el dato concreto que la disparó (la query del assertion te lo da en la pestaña Failed assertions de Dataform). Decide: ¿es un bug de origen que hay que escalar a HRIS? ¿o la regla de negocio cambió y la assertion está desactualizada? Solo cuando lo sepas, ajustas.
